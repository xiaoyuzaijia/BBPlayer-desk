## 一、需求清单

### 1.1 范围决策

| # | 项 | 决策 |
|---|---|---|
| Q1 | 歌词源 | **QQ 音乐 + 酷狗**，不做网易云 |
| Q2 | 逐字歌词 UI | **不做**逐字 UI（splash 仍保留 `spans` 类型，但 UI 不渲染） |
| Q3 | 翻译歌词 | **不获取** tlyric（QQ/酷狗均不主动取翻译） |
| Q4 | 罗马音 | **不获取** romalrc |
| Q5 | 歌词偏移量 | **不做** |
| Q6 | 手动搜索 | **不做**，仅自动获取 |
| Q7 | 手动编辑 | **不做** |
| Q8 | 跳过标记 | **不做** |
| Q9 | 预加载 | **不做**，仅进歌词页才查询 |
| Q10 | B 站歌名反查 | **做**（`bilibiliApi.getWebPlayerInfo` → `bgm_info.music_title` → `《...》` 提取精确歌名） |

### 1.2 架构决策

| # | 项 | 决策 |
|---|---|---|
| Q11 | 持久化介质 | **文件系统** `userData/lyrics/{uniqueKey}.json`（与 BBPlayer 一致，不进 SQLite） |
| Q12 | SPL 解析包 | **1:1 复刻** `@bbplayer/splash` 到 `src/renderer/utils/splash/`（已完成） |
| Q13 | 类型升级 | **升级** `LyricLine` 到 BBPlayer 完整版（含 `spans` / `romaji` / `isDynamic` / `endTime`） |
| Q14 | 解析位置 | **渲染进程解析**（IPC 传 SPL 字符串 `{lrc}`，渲染进程调 `parseAndMergeLyrics`） |
| Q15 | 网易加密实现 | **跳过网易**，仅做 QQ + 酷狗（均无加密） |
| Q16 | facade vs service 编排 | **编排放 facade 层**（`LyricFacade`），service 只做单表 CRUD（与项目架构一致，与 BBPlayer 偏离） |
| Q17 | 多源竞速实现 | **`Promise.any` + `AbortController`**（与 BBPlayer 一致） |
| Q18 | 进度驱动 | **渲染进程 `requestAnimationFrame` 平滑插值**（参考 BBPlayer `useSmoothProgress`） |

### 1.3 UI 决策

| # | 项 | 决策 |
|---|---|---|
| Q19 | LyricView 改造方式 | **保留现有 35% 偏上定位 + mask-image 渐变 + 点击 seek**，仅换数据源 + 适配新类型 + 加 2s 防抖 |
| Q20 | 手动滚动防抖 | **做** 2s 防抖回弹（与 BBPlayer 一致） |
| Q21 | 逐字 UI | **不做** |
| Q22 | 歌词页控件覆盖层 | **不做**，控件就在歌词页左边（现有布局） |

### 1.4 不做的事

- 网易云音乐歌词源（含 YRC 逐字、eapi/weapi 加密）
- 翻译歌词、罗马音歌词
- 逐字卡拉OK UI（`KaraokeWord`）
- 歌词偏移量调整面板
- 手动搜索模态、手动编辑模态
- 跳过标记（`manualSkip`）
- 切歌预加载下一首歌词
- 歌词分享卡片
- 桌面歌词 / 状态栏歌词 / 车机歌词 overlay
- 歌词页控件覆盖层（滚动方向联动 + 自动隐藏）

### 1.5 关键约束

1. **不获取翻译/罗马音**：QQ 音乐 API 虽返回 `trans` 字段，但本次**不读取**（`parseLyrics` 直接 `tlyric: undefined`）；酷狗 API 本就不支持翻译
2. **不渲染逐字**：splash 的 `parseSpans` 仍会解析出 `spans`，但 `LyricLineItem` 不渲染 `KaraokeWord`
3. **持久化仅 `lrc` 字段**：缓存文件结构简化为 `{ id, updateTime, lrc, errorMessage? }`，无 `tlyric` / `romalrc` / `manualSkip` / `misc`
4. **解析在渲染进程**：主进程只传 SPL 字符串，IPC 数据量小；渲染进程持有 `LyricLine[]` 后续计算（当前行索引、滚动定位）都在本地

### 阶段 4：主进程 LyricFacade（多源竞速 + B 站歌名反查）

**做什么**：新建 `LyricFacade`，编排「文件缓存 → B 站歌名反查 → 多源竞速 → 落盘」全流程。与 `PlaybackFacade` 模式一致（含 `pendingRequests` 并发去重）。

**改动文件**：

1. **`src/main/lib/facades/lyric.ts`**（新建）
   - `class LyricFacade` + `initLyricFacade()` + `getLyricFacade()` 单例
   - 构造注入：`lyricService` + `qqMusicApi` + `kugouApi` + `bilibiliApi`（用于 `getWebPlayerInfo`）
   - 主入口方法：
     ```ts
     getLyric(trackId: number): ResultAsync<LyricFileData, LyricFacadeError>
     ```
   - 流程：
     1. `trackService.getTrackById(trackId)` 拿 track（含 `uniqueKey` / `title` / `duration` / `bilibiliMetadata`）
     2. `lyricService.getLyricFile(track.uniqueKey)` 查缓存，命中（有 `lrc` 字段或 `errorMessage`）直接返回
     3. cache miss → 走网络：
        - 若 `track.source === 'bilibili'`：调 `bilibiliApi.getWebPlayerInfo({ bvid, cid })` → 从 `data.bgm_info.music_title` 提取 `《...》` 内容作 `preciseKeyword`
        - 否则用 `cleanKeyword(track.title)`（剥除 `【...】` / `"..."` 标记）
        - 调 `getBestMatchedLyrics(track, keyword, 'auto')`
     4. `processAndSaveLyrics`：组装 `LyricFileData` → `lyricService.saveLyricFile`
   - `getBestMatchedLyrics(track, keyword, source)`：
     - `source === 'auto'`：为 qq/kugou 各创建独立 `AbortController`，`Promise.any` 竞速，首个成功 abort 其余
     - `source === 'qqmusic'` / `'kugou'`：仅查单源
     - 全失败：聚合错误消息构造 `LyricNotFoundError`，包装成 `LyricFileData { errorMessage }` 落盘（避免反复重试）+ 返回该 `errorMessage` 版本
   - **并发去重**：`pendingRequests: Map<trackId, ResultAsync>`，同一 trackId 同时只发一次网络请求（复用 `PlaybackFacade` 模式）
   - **不做**：`manualSkip` 检查、`preloadNextTrackLyrics`、`pushLyricsToOverlays`、`migrateFromOldFormat`

2. **`src/main/lib/errors/facade.ts`**（追加）
   - `FacadeErrorType` 追加 `'LyricFetchFailed'`
   - 不新增工厂函数，复用 `createFacadeError`

3. **`src/main/lib/facades/lyric.ts` 中的 `LyricFacadeError`** 联合类型：
   ```ts
   type LyricFacadeError = FacadeError | ThirdPartyError | ServiceError | BilibiliApiError
   ```
   注：不含 `DatabaseError`（lyricService 不用 DB），但含 `BilibiliApiError`（`getWebPlayerInfo` 失败时）

**对应 BBPlayer**：`apps/mobile/src/lib/services/lyricService.ts` 中的 `smartFetchLyrics` / `getBestMatchedLyrics` / `getPreciseMusicNameOnBilibiliVideo` / `cleanKeyword` 逻辑，**但全部移到 facade 层**（Q16 决策）。`pendingRequests` 模式参考项目内 `src/main/lib/facades/playback.ts`。

**验证**：主进程调 `getLyricFacade().getLyric(trackId)`，对一首 bilibili track 能拿到 `{ lrc: '...', updateTime }` 或 `{ errorMessage: '...' }`，且 `userData/lyrics/` 下有对应 JSON 文件。

## 五、风险与注意事项

1. **BBPlayer `NeteaseApiError` 的 `vendor: 'Bilibili'` bug**：本次跳过网易，不涉及此 bug
2. **酷狗 API 用 http 不是 https**：Electron 主进程 `undici` 默认允许 http，但需确认无 mixed content 警告（主进程无此限制，仅渲染进程有）
3. **`getWebPlayerInfo` 失败时的 fallback**：B 站歌名反查失败不应阻塞歌词获取，应 fallback 到 `cleanKeyword(track.title)` 继续走多源竞速
4. **`Promise.any` 的 `AggregateError`**：全失败时需提取各源错误消息拼接成 `errorMessage` 字符串，落盘时存入 `LyricFileData.errorMessage`
5. **`staleTime: 0` + 文件缓存**：每次进歌词页都会触发 query，但 facade 内部文件缓存命中时不联网，性能可接受
6. **splash 包的 `parseYrc` 死代码**：本次不调网易源，`parseYrc` 不会被调用，但保留不影响（纯函数无副作用）
7. **`uniqueKey` 路径安全**：`uniqueKey` 含 `::`（如 `bilibili::BV1xxx`），写文件前必须 `replaceAll('::', '--')`
8. **`requestAnimationFrame` 在后台标签页**：Chromium 后台标签页会降频 rAF，歌词同步可能卡顿；但本项目是 Electron 窗口，播放时通常在前台，可接受
9. **`parseAndMergeLyrics` 入参**：本次仅传 `{ lrc }`（无 `tlyric` / `romalrc`），splash 内部会跳过合并逻辑直接返回 `LyricLine[]`
10. **阶段 1 类型升级的连锁影响**：升级 `LyricLine` 类型后，所有引用旧字段（`time` / `text`）的文件都会报错，必须在阶段 7 一并修复；阶段 1 完成后 `pnpm typecheck` 会失败，属正常
